# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A single-user (mono-utilisateur) mobile-first PWA for tracking airport-porter missions ("interventions") and tips ("pourboires"). It's a personal app, separate from the (external) schedule-extractor tool — it only consumes reports produced elsewhere. All UI copy, comments, and domain terms are in French; keep new code consistent with that.

## Commands

```
npm install
npm run dev       # vite dev server
npm run build      # production build to dist/
npm run preview    # preview the production build
```

There is no test suite and no linter configured in this repo.

Requires `.env.local` with `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY` (see README.md for full Supabase project setup — schema lives in `supabase/schema.sql` and must be run manually in the Supabase SQL editor; public signups must be disabled since this is single-user).

## Architecture

**Stack**: React + Vite, Tailwind CSS v4 (config lives in `@theme` inside `src/index.css`, not a tailwind.config file), zustand for state, Dexie (IndexedDB) for local cache, Supabase (Postgres + Auth) as the remote source of truth, vite-plugin-pwa for installability.

**Two domain entities**, both synced the same way: `missions` (an intervention/job) and `work_shifts` (a workday, used to compute €/hour — also doubles as the record of OFF days, worked or not, see the Shift/overtime math note below). Postgres schema, including RLS policies scoped by `auth.uid() = user_id`, is in `supabase/schema.sql`.

**Offline-first sync model** (`src/lib/sync.js`, backed by `src/lib/db.js`):
- Every record gets a client-generated UUID at creation time, making writes idempotent (`upsert`) — safe to retry without creating duplicates.
- Local writes go to Dexie first (`syncStatus: 'pending'`), then `flush()`/`flushShifts()` push pending/`error`/`pending-delete` rows to Supabase opportunistically (on save, on `online` event, on app init via `initSync()`). Rows that fail to sync are marked `error` and are **retried on every subsequent flush**, not dropped. Both flush loops guard against a concurrent local edit racing the network call: after a successful upsert, a row is only flipped to `synced` if `current.updated_at === m.updated_at` still holds — if the record was edited again locally while the request was in flight, it's deliberately left `pending` so the newer edit still gets pushed on the next flush. Calling `flush()`/`flushShifts()` while a flush is already in progress doesn't start a second overlapping pass; it just flags a rerun so the in-flight pass loops once more after finishing.
- `initSync()` and `useMissions.init()` both flush before pulling (same order as the `online` handler below), not just on reconnect — a pull that raced ahead of a flush at app-open time (the common way a queued offline write reaches connectivity) could otherwise clobber a just-flushed edit with stale server data, or resurrect a row just deleted.
- `flushShifts()` self-heals a specific legacy failure mode before upserting: a shift with a missing/invalid `start_min`/`end_min` used to make `workedMin()` return `NaN`, which serializes to `null` and gets rejected by the `hours numeric not null` constraint, leaving the row stuck in `error` forever (the flush only resends whatever's already in Dexie — it never recomputed). If `Number(s.hours)` isn't finite, it now recomputes the row via `recompute()` (itself defensive against missing fields, see the Shift/overtime math note) before building the payload. No manual "repair" step should be needed for this again.
- That self-heal only ever touches rows still `pending`/`error` — a row that's already `synced` with a stale-but-numerically-valid derived field (e.g. `night_hours: 0` on a shift saved before night-hour tracking existed in `parseShift.js`, added 2026-06-30) is never revisited by anything automatic. A one-off repair tool (`useMissions.recalcAllShifts()` + `Home.jsx`'s `RecalcShiftsSection` button, in the same spirit as the earlier `repairStuckShifts`) was added to backfill exactly that gap for existing data, used once, then removed — if a future change to `recompute()`'s logic needs the same kind of backfill again, recreate a similar tool rather than resurrecting this one from history.
- Deletes go through the same queue: `deleteMission`/`deleteShift` delete immediately (local + remote) when online and the remote call succeeds; otherwise the row is kept locally and flipped to `syncStatus: 'pending-delete'` so the deletion is retried and propagated once back online, instead of being silently lost. `loadAll()`/`loadShifts()` filter out `pending-delete` rows so they disappear from the UI immediately regardless.
- `pullFromServer()`/`pullShifts()` merge remote rows into Dexie, but **skip any local row still `pending`, `error`, or `pending-delete`** so an unsynced local write/delete is never clobbered by a stale server read. The `online` event handler runs `pullFromServer`/`pullShifts` after flushing, so reconnecting also reconciles rows changed remotely (e.g. from another device) while this one was offline.
- `useOnline.js`'s `useSyncStatus(missions, shifts)` counts pending/error/pending-delete rows across **both** tables for the sync indicator in `App.jsx` — pass both arrays, not just `missions`, or shift-only changes won't refresh the badge.
- Each entity module (`saveMission`/`saveShift`, etc.) whitelists a fixed `COLUMNS`/`SHIFT_COLUMNS` array before writing to Supabase — when adding a new field to a mission or shift, update both the Postgres schema and this column whitelist, or it will silently not sync.

**State layer** (`src/store/missions.js`): a single zustand store (`useMissions`) holding both `missions` and `shifts` in memory, backed entirely by the `sync.js` functions above — components never talk to Dexie or Supabase directly.

**Text-paste import pipeline** (`src/lib/parseImport.js` → `parseReport.js` / `parseShift.js`): the user pastes freeform report text (from the external scheduling tool) into `ImportModal`; `parseImport` sniffs the content (a Booking field → mission reports, a `d/m : Hh - Hh`-style pattern → shift ranges) and routes to the matching regex-based parser. These parsers are tolerant/best-effort (French labels, accented/unaccented variants, `OUI`/`NON`-style booleans) — when extending them, follow the existing pattern of one `val(text, 'Label')`-style field extractor per field rather than a single monolithic regex. `normService()`/`normBookingMode()` both run values through `stripAccents()` (NFD-normalize + strip combining diacritics) before comparing — without it, `'Départ'.toUpperCase()` is `'DÉPART'`, and `'DÉPART'.startsWith('DEP')` is `false` (É ≠ E), so `normService()` used to silently default every imported "Départ" mission to `'ARR'` (Arrivée) until this was caught; `normBookingMode()` had already worked around the same class of issue ad hoc for "Pré-booking" before both were switched to the shared helper. The Booking field's `#` has moved sides between template revisions — `"Booking # : 30502"` (label-side) vs `"Booking : #30502"` (value-side, the external tool's current format) — so `parseReport.js` exports a single `BOOKING_FIELD_RE` tolerating `#` on either side, shared by the sniff test (`parseImport.js`), the multi-report chunk-splitter (`parseReports()`), and `booking_ref` extraction, specifically so these three don't drift out of sync with each other again (they already did once, when only the sniff/splitter were updated for the new format and `booking_ref` extraction was left on its old, narrower pattern). `booking_ref` still strips a leading `#` defensively so it's stored consistently regardless of source format (`ImportModal.jsx`'s preview list prepends its own `#`). Separately, `parseReport.js`'s "problème rencontré" capture must not have a greedy `\s*` between the `?` and the capture group: with one applied, an **empty** problem section makes that `\s*` swallow all blank lines up to the next section's first non-whitespace character, which then prevents the next section-number terminator (`\n\s*\d+\.`) from matching (it needs a leading `\n`) — the capture silently overruns into the *following* numbered section, wrongly setting `has_issue: true` with garbage `issue_description`. Keeping the leading whitespace inside the lazy capture group itself (rather than a separate greedy quantifier before it) lets the terminator match at position zero when the section is genuinely empty. `ImportModal`'s preview step is asymmetric between the two content types: parsed shifts get a per-row OFF toggle before saving (`recompute(s, isOff)` applied at confirm time), while parsed missions have no pre-save review at all (`addMany(result.items)` straight from the parser's output) — correct by design since missions have no equivalent ambiguous flag to confirm, but worth knowing before assuming both preview lists behave the same way. `useMissions.addShifts()` overwrites-in-place rather than duplicating: for each imported shift it looks up an existing shift with the same `shift_date` and, if found, reuses that shift's `id` (so `saveShift()` updates the same Dexie/Supabase row) instead of minting a new one — re-pasting a corrected schedule for a period already entered replaces the overlapping days rather than doubling them. `addShifts()` is also called from `Calendar.jsx`'s single-shift create paths (`saveEdit()`/`markRestDay()`), but only in the branch where no shift is already selected for that date (`else await addShifts([...])`), so the lookup can never find a match there — the dedup logic is effectively import-only in practice even though the function itself isn't. `addMany()` (missions) has no equivalent dedup — every parsed mission always creates a new row, since missions don't have a natural one-per-date identity the way shifts do.

**`val()`'s field-value capture is bounded to the label's own line** (`src/lib/parseReport.js`): the regex used to be `label\s*:\s*(.+)` — since `\s` matches `\n`, an **empty** field's value made `\s*` after the colon skip past the (empty) rest of that line, through the newline, and keep consuming leading whitespace until it hit the next label's text, which `(.+)` then captured as if it were this field's value (e.g. `"Client : \nGreeteur : X"` attributed `"Greeteur :"` to `client_name`, leaving `greeter` itself empty and every field after it shifted/corrupted in the worst case). Now `[ \t]*:[ \t]*(.*)` — horizontal whitespace only around the colon, and `(.*)` allowing a genuinely empty match — so the capture can never cross a line boundary, and an empty field correctly returns `''` instead of stealing the next label's text. `BOOKING_FIELD_RE`'s shared pattern (see above) had the identical bug for the same reason and got the same fix (`[ \t]*` in place of `\s*` around the `#`/`:`), so an empty/missing booking ref no longer bleeds into whatever field follows it. Found via `formatMissionReport()`'s round-trip test (see below) with a mission that had several blank optional fields — real pasted reports rarely have blank fields (every mission has a real client/booking/etc.), which is likely why this went unnoticed until a systematic round-trip test exercised it.

**"Copier le rapport" button** (`MissionForm.jsx`, shown only when editing an existing mission): reconstructs the mission as plain text via `formatMissionReport()` (`src/lib/formatReport.js`) and copies it to the clipboard (`navigator.clipboard.writeText`), with the button label flipping to "Copié !" for 1.5s as feedback. `formatMissionReport()` deliberately reuses the exact field labels `parseReport.js`'s `val(text, 'Label')` calls expect (`Date`, `Booking`, `Client`, `Greeteur`, `Pré-booking ou Live`, `Type de service`, etc.), so the copied text can be pasted straight back into the import flow and reparses to an equivalent mission for almost every field — verified with a dedicated round-trip test rather than assumed. The one field ordering constraint this imposes: `Problème rencontré ?` **must** stay the last line, because `parseReport.js`'s issue-capture regex only terminates at a `\nN.` numbered section (which this reconstructed report has none of, unlike the external tool's original template) or end-of-string — anywhere else, the capture would run past it and swallow every field that follows (caught by the same round-trip test before this shipped). `Pourboire` (the tip amount) is included for the user's own record even though it isn't part of `parseReport()`'s import format at all (tips are entered manually after import, never parsed from the pasted text). **Known, accepted gap** (found in review, not fixable without touching the real import parser): `is_no_show` and `has_issue` are two independent booleans in the form (two separate buttons), but `parseReport()` derives both from the same "Problème rencontré ?" line — a mission with `is_no_show: true` and `has_issue: false` (no-show marked without also flagging "Problème signalé") has no distinct textual representation, so copying and re-pasting it flips `has_issue` to `true` with a fabricated `issue_description: "No show"`. Left as-is rather than reworked, since fixing it would mean changing how real pasted reports from the external tool are parsed, which is out of scope and risks regressing the primary import path.

**Hours-only PDF export sizes its own page instead of using a full A4 with a large empty tail** (`exportPayrollPdf`'s `estimateHoursOnlyBottom()` in `src/lib/exportPayroll.js`): when `hoursOnly` is true and exactly one month is being exported (the only shape `PayrollSimulator.jsx` ever calls with), the function precomputes the exact content height in mm — mirroring the same `y` increments the drawing loop below it uses — and, if that fits under the existing 280mm single-page threshold, constructs the `jsPDF` document with a custom `[210, height]` page size instead of a fixed 297mm-tall A4, eliminating the large blank area a short month's report used to leave at the bottom of the page. Content that doesn't fit on one page (`estimated > 280`, or a multi-month array) falls straight back to standard A4 with the existing pagination logic untouched. One non-obvious gotcha: jsPDF's `orientation: 'portrait'` (the default) silently **swaps** width and height whenever the given format's width exceeds its height, to enforce portrait's width-≤-height invariant — since a short month's custom height is deliberately *less* than the fixed 210mm width, portrait mode would have swapped them and broken every column's x-position (all calibrated assuming a 210mm-wide page). Passing `orientation: 'l'` avoids the swap in that case (landscape's invariant is width-≥-height, already satisfied); for the rarer case where the estimated height instead exceeds 210mm (a longer month, still under the 280mm cutoff), the orientation choice flips to `'p'` for the same reason, in the other direction. This `orientation` value is purely a technical lever to prevent jsPDF's auto-swap — it has no relation to the page's actual visual orientation, which is always a tall/narrow "portrait-shaped" hours table regardless of which literal string is passed.

**"Détail des heures" carries a caption explaining the Sup column's break deduction** (`exportPayrollPdf`/`exportPayrollXlsx` in `src/lib/exportPayroll.js`): a small italic line — "Sup : heure de pause (1h) déjà retirée du calcul." — sits between the section title and the table header (PDF) or between "DÉTAIL DES HEURES" and the header row (Excel), clarifying that `overtimeMin()` (`parseShift.js`) already subtracts the 1h gap between `NORMAL_SHIFT_MIN` (7h30) and `BASE_SHIFT_MIN` (8h30) before counting anything as overtime — added because the Sup figure for a given shift can otherwise look lower than a naive "hours worked minus 8h30" mental model would predict. In the PDF, this line needed **7mm** of clearance before the table header starts (not the original 5mm), or its descenders visually clipped into the table's top border — `estimateHoursOnlyBottom()`'s precomputed height must stay in sync with this spacing (`8 + 7 + 7` for title + caption + header) since it mirrors the drawing loop's exact increments.

**Shift time-range formats accepted by `parseShifts()`** (`src/lib/parseShift.js`): the canonical "d/m : Hh(mm) - Hh(mm)" (hyphen-separated) format is not the only one in the wild — a colleague's notation drops the hyphen entirely and/or appends a trailing period after each time (`"7h.  17h30"`, `"9h 17h"`, `"13h30 23h"`), so the hyphen between the two times is optional and each time tolerates a trailing `.`. `shiftLineSource(withCaptures)` builds the regex source from shared `H`/`M` fragments and is reused both by `parseShifts()` itself (`withCaptures=true`, for the actual field extraction) and by `SHIFT_LINE_RE` (`withCaptures=false`, exported for `parseImport.js`'s content-type sniff) — same rationale as `BOOKING_FIELD_RE` above: keep the detection and extraction patterns from silently drifting apart.

**Shift/overtime math** (`src/lib/parseShift.js`): shifts are stored as `start_min`/`end_min` (minutes from midnight, wrapping past 1440 for overnight shifts). Night hours are 22:00–07:00. Overtime is "worked beyond 8h30 (`BASE_SHIFT_MIN`)", except on a declared day off (`is_day_off`) where the *entire* shift counts as overtime (`overtimeMin()`). `workedMin()`/`nightBreakdown()` coerce `start_min`/`end_min` via `Number(...) || 0` — defends against legacy/corrupted rows with a missing field producing `NaN` (see the `flushShifts()` self-heal note above for why that mattered). `overtimePayMin()`/`night_overtime_hours` no longer bake in any day-off premium — `overtime_hours`/`night_overtime_hours` are plain, unmultiplied durations regardless of `is_day_off`; the pay premium is applied later, only in `src/lib/payroll.js`. Night-overtime is computed as the overlap between the night window and the *tail* of the shift (overtime is defined as occurring at the end of the shift). If you change shift editing logic, use `recompute()` to keep `hours`/`overtime_hours`/`night_hours`/`night_overtime_hours` consistent rather than recalculating ad hoc. A **rest day** (day off, not worked at all) reuses the same `is_day_off` flag but with `start_min`/`end_min` both `0` — `recompute({start_min:0,end_min:0}, true)` naturally yields all-zero fields, no schema change or new column needed. `isRestDay(shift)` (`is_day_off && !hours`) is the single predicate distinguishing this from a worked day off, used everywhere it's displayed (`Calendar.jsx`'s grid label and day-detail panel, `shiftRows.js`'s `shiftRowCells`). For **display/export purposes** (`summary.js`'s `overtime`/`offWorked`, `monthlyDetail.js`'s totals and the `Sup`/`OFF trav.` export columns, `Home.jsx`'s "Heures travaillées (OFF)" tile), normal overtime and worked-day-off hours are still split on `is_day_off` and shown as separate figures. For **payroll purposes** (`src/lib/payroll.js`), a worked day off's hours are merged into the same monthly overtime pool as real overtime and tiered on the same 33h/50% threshold — see the "Payroll simulator" note below for the history of this decision (it replaced an earlier design where worked-day-off hours were a separate flat +25% bonus excluded from the pool).

**Calendar day-detail panel** (`src/components/Calendar.jsx`): the panel below the grid is a 4-way branch on `editing`/`selShift`/`isRestDay(selShift)`, in that priority order — the time-entry form, a dedicated "Jour OFF — non travaillé" block (offers "Ajouter des horaires" to convert it into a worked day off, or delete it), the full worked-shift breakdown (Row list + the "Marquer ce jour comme OFF travaillé" toggle), and finally the empty-day state which now offers two actions — "Ajouter shift" (header button, opens the time form) and, in the body below, "Marquer comme jour OFF (non travaillé)" (creates the zero-hour rest-day shift directly, no form). The small red dot drawn on any `is_day_off` grid cell is the same one the legend's "jour OFF" entry has always described — it just wasn't actually rendered until the rest-day feature was added. The time-entry form's live preview (`Brut`/`Sup`/`Nuit` row) recomputes `nightBreakdown()` on every keystroke so night hours (22h-7h overlap on either end of the shift) are visible before saving — added after a real payslip showed night-hour premiums the simulator wasn't reflecting, which turned out to be a data-entry gap (no shift actually logged with clock times crossing the window) rather than a bug in `nightBreakdown()` itself.

**Stats/aggregation** (`src/lib/summary.js`, `charts.js`): two modules compute overlapping-but-distinct views (bucketed history by day/week/month/year, current-period totals, chart-ready bar data) from the same `missions`/`shifts` arrays. (A third module, `aggregate.js`, duplicated much of this with extra `tipPerHour`/`tipPerPax`/no-show-exclusion logic; it was never imported anywhere and was deleted as dead-code cleanup — don't resurrect that logic from history without re-checking it's still wanted.) ISO week numbering is duplicated in **three** live places (`summary.js`, `charts.js`, and inline in `Home.jsx` for the period-nav label) — keep them in sync if fixing week-boundary bugs. `src/lib/format.js` holds the two formatting primitives (`eur()`, French `MONTHS`) shared by `dispatch.js`/`Home.jsx`/`Calendar.jsx`/`MissionsList.jsx` — new code needing either should import from here rather than redeclaring them. `monthlyDetail.js` keeps its own separate `MONTHS` literal (identical values, not imported from `format.js`) — a second, smaller duplication that's harmless today but won't stay in sync automatically if the wording/locale ever changes.

**Home's period navigation** (`src/components/Home.jsx`): the Semaine/Mois/Année tabs pair with a `refDate` state and ‹›  arrows that step `refDate` by one unit of the selected period (`shiftRefDate`); `summary(missions, shifts, period, refDate)` already accepts an arbitrary reference date, which is what makes this work — the "next" arrow disables once `periodKey(period, refDate)` matches today's, so you can't scroll into the empty future. Switching tabs resets `refDate` back to now. The "Moyenne par jour travaillé" card is always scoped to the calendar month of `refDate` (`d.getFullYear()`/`d.getMonth()`, independent of which tab is active) rather than all-time history, with a small month/year label next to its title so the scope stays visible even on the Semaine/Année tabs.

**Amount privacy blur** (`src/components/Home.jsx`): every € figure on Accueil (Gains totaux, the bar-chart values/tap-detail, the daily-average and Max/Min, and the dispatch split) is blurred behind a single page-wide `revealed` boolean and only clears on tap. The secondary amounts (bar-chart tap-detail, daily-average/Max/Min, dispatch split) go through the local `Amt` wrapper component (`filter: blur(...)`, toggled `onClick`); the main "Gains totaux" figure and the in-chart SVG bar labels hand-roll the identical `filter: blur(...)` pattern inline instead (plain markup/SVG `text`, not a wrapper component, for layout reasons) rather than using `Amt` itself. Only the main "Gains totaux" figure carries an explanatory hint ("Touche le montant pour l'afficher") — new amounts added to this page should reuse the same `revealed`/`toggleRevealed` blur pattern (via `Amt` where the markup allows it) without adding their own hint text.

**Dates**: always stored/compared as `YYYY-MM-DD` local-date strings (`src/lib/date.js`: `todayLocal()`/`parseLocal()`), specifically to avoid UTC-shift bugs — never use `new Date(dateString)` directly on these values, and don't default a month/day key via `new Date().toISOString()` either (that's UTC, not local) — `PayrollSimulator.jsx`'s default `monthKey` uses `todayLocal().slice(0, 7)` for this reason.

**`work_shifts.hours`/`overtime_hours` are `numeric(5,2)`** (`supabase/schema.sql`), matching `night_hours`/`night_overtime_hours` — they used to be `numeric(4,1)` (1 decimal), which made Postgres silently round a quarter-hour shift (e.g. 3.75h) to the nearest 0.1h (3.8h) on write, corrupting the duration on the next server round-trip. If your Supabase project predates this fix, run the commented `alter table ... alter column ... type numeric(5,2)` migration at the bottom of `schema.sql` manually.

**Only overtime and worked-OFF-day hours follow the 25th payroll cutoff — base and night hours stay on the real calendar month** (`src/lib/monthlyDetail.js`'s `payrollCutoffMonthKey()`): the employer's payroll closes overtime/jour-OFF accounting on the 25th — a shift dated the 1st–25th of a calendar month has its overtime/off-worked hours counted in that month's payslip, a shift dated the 26th–end has them counted in *next* month's payslip instead. Verified against a real bulletin de salaire, where the cumulative "heures sup" figure was below the full calendar month's total. Crucially, this cutoff does **not** apply to everything: `monthlyDetail()` keeps two separate groupings — `rows` (the day-by-day ledger) and `total.baseHours`/`total.night` are grouped by the shift's real calendar month, while only `total.overtime`/`total.offWorked` are grouped by the cutoff month. A shift dated June 27th, for example, still appears under June's day-by-day rows with its base hours counted in June's payroll, but its overtime portion is added to July's overtime pool. (An earlier version of this cutoff wrongly applied it to the whole month grouping, which silently dropped late-month base/night hours from that month's totals — caught and fixed after comparing against a real payslip.) This only changes `monthlyDetail()`'s output shape (`total.baseHours` replaces the old `total.hours - total.overtime` subtraction in `payroll.js`) — it does **not** touch `summary.js`/`charts.js`/`Home.jsx`, which stay on real calendar months for stats/history; `monthlyDetail()` is used exclusively by `payroll.js`, so the payroll simulator and its PDF/Excel exports are the only things affected.

**"Dont heures sup. du mois dernier" row** (`payrollRows()` in `src/lib/payroll.js`): since the carry-in described above folds silently into `total.overtime`, `monthlyDetail()` also tracks `total.overtimeCarriedIn` as a separate sub-total — the portion of the current month's overtime pool that actually came from the previous month's 26th–end shifts (determined by comparing each shift's real calendar month to its `payrollCutoffMonthKey()`). Includes both real overtime and worked-day-off hours (`carriesOver(s)` doesn't check `is_day_off`) — the two are now merged into the same payroll pool (see the "Payroll simulator" note below), so a carried-in worked-OFF-day shift's hours must count here too, or this row would undercount relative to the "Heures sup jusqu'à 33h"/"à partir de 34h" totals it's meant to explain. (An earlier version scoped this to `!is_day_off` overtime only, back when worked-day-off hours were their own separate flat bonus outside the pool — no longer applicable.) `payrollRows()` shows this as its own informational row (only when `overtimeCarriedInHours > 0`), positioned right before "Heures sup jusqu'à 33h"/"à partir de 34h", so the reader can see how much of the tiered total below was contributed by last month. The label spells out "Dont... (déjà incluses ci-dessous)" rather than just "Heures supplémentaires du mois dernier" — without that qualifier the row renders identically (same `Row` component, same PDF/Excel styling) to the genuinely-additive category rows around it, and a reader comparing against a real payslip could misread it as extra hours on top rather than a breakdown already counted below, and flag a false discrepancy. It also deliberately has **no** `amount` of its own (`amount: null`, rendered as "—" in the UI/PDF/Excel) — its hours are already counted inside `overtimeLowHours`/`overtimeHighHours` and their corresponding amounts, so giving it a separate € figure would double-count it in `grossTotal` (which is computed independently in `computeMonthPayroll()`, not by summing `payrollRows()`'s displayed amounts, so this null-amount row doesn't affect any total). `eur()` in `exportPayroll.js` and the `Row` component in `PayrollSimulator.jsx` both special-case `amount == null` → `'—'`, distinct from a real `0` amount (e.g. "Heures sup à partir de 34h" legitimately shows "0.00 €" when unused).

**Carried-in and carried-out shifts in the "Détail des heures" table** (`monthlyDetail()`'s `carriedInRows`/`carriedOutRows`/`ownCountedRows`/`cutoffRows`, consumed by `exportPayrollPdf`/`exportPayrollXlsx`): the recap row above explains the carry-in as a number, but the day-by-day hours table (PDF/Excel) goes further and shows the *actual shifts* on both sides of the 25th cutoff. `carriedInRows` are the previous month's 26th–end shifts whose majoration (overtime **or** worked-OFF-day hours — both follow the same cutoff, see `carriesOver()`) rolled into this month's payroll pool; `carriedOutRows` are the mirror image — this month's own 26th–end shifts whose majoration instead rolls *out* to next month's pool. Both are rendered under their own italic section label ("Report du mois précédent (après le 25) :" / "Reporté au mois prochain (après le 25) :"), bracketing the month's own counted rows (`ownCountedRows = rows` minus `carriedOutRows`), each label only shown when its section is non-empty. `monthlyDetail()` collects `carriedInRows` while building `cutoffMap` (any shift with `cutKey !== calKey` and `carriesOver(s)`, i.e. `overtime_hours > 0`, regardless of `is_day_off`) and derives `carriedOutRows`/`ownCountedRows`/`cutoffRows` (`= [...carriedInRows, ...ownCountedRows]`) per month in the same pass — all four are precomputed once here and forwarded verbatim through `computePayroll()` in `payroll.js`, rather than each export function recomputing its own copy (same rationale as `BOOKING_FIELD_RE` in `parseReport.js`: two independent derivations of the same thing risk drifting apart the next time only one gets edited). The `Total` row underneath sums two *different, precisely-scoped* row sets, not `p`'s totals: `Durée`/`Nuit` sum over `m.rows` in full (the complete real-calendar-month ledger, including carried-out rows — their duration/night hours stay this month's regardless of cutoff), while `Sup`/`OFF trav.` sum over `cutoffRows` — i.e. exactly the rows visibly counted in this table under a "counted" label. `shiftTotalsRow(calendarRows, cutoffRows)` takes both sets explicitly (no longer optional) for this reason. An earlier version imposed `Sup`/`OFF trav.` directly from `p.overtimeLowHours + p.overtimeHighHours`/`p.offWorkedHours` instead of summing the displayed rows — numerically equal in theory, but it silently desynced from what was on screen whenever a carry-out existed (a shift shown in the table but excluded from Total, no explanation) and, worse, never surfaced worked-OFF-day carry-*in* shifts at all (a paid "Prime jour OFF" bonus in the recap with zero supporting rows anywhere) — both caught in review and fixed by switching to this row-derived total, which can't drift from what the reader can see and add up themselves. `computePayroll()` must forward all four fields from `monthlyDetail()`'s output onto each month's result — an early pass at this fix forgot `carriedOutRows`, which silently no-opped the whole carry-out split (caught immediately by re-testing against the same review scenarios before merging).

**"Heures normales" (`total.baseHours` in `monthlyDetail.js`) is a flat 7h30/worked-day (`NORMAL_SHIFT_MIN`, `src/lib/parseShift.js`), not the shift's actual hours minus its overtime.** The 1h gap up to `BASE_SHIFT_MIN` (8h30, where overtime starts) is an implicit unpaid break already baked into the existing overtime threshold — confirmed against the user's real hour tracker, where every non-OFF shift shows exactly "7h30" of normal hours regardless of its actual duration (as long as it reaches 8h30), with the surplus going entirely to `overtime_hours`. Below 8h30 the formula doesn't hold flat at 7h30 or drop to 0 — it ramps down linearly (`max(0, workedMin - 60)`, i.e. worked time minus the same 1h break), which is **unverified against a real payslip** (the only real data point checked was full 8h30+ days); revisit if a genuinely short (<6h) worked shift ever needs a payslip comparison. A worked day off (`is_day_off`) contributes **zero** to `baseHours` — its hours live entirely in the separate `offWorked`/"Prime jour OFF" bucket (see above), never double-counted as normal hours too (an earlier version of `baseHours` incorrectly counted a worked day off's full duration as normal hours on top of the OFF-day premium — caught and fixed after comparing against the user's real hour tracker).

**`rows` in `monthlyDetail()` excludes rest days** (`isRestDay(shift)` from `parseShift.js`: `is_day_off && !hours`, a declared day off with zero hours, distinct from a *worked* day off which has real hours/overtime) — filtered out where `rows` is built (`(calendarMap.get(key) || []).filter(s => !isRestDay(s))`), before it feeds both the "Détail des heures" display and `baseHours`/`night`. Safe to filter at the source rather than only at display time: a rest day always contributes `0` to every one of those totals already (`baseHours`'s reducer already skips any `is_day_off` row; `night` sums a field that's `0` on a shift with no hours), and `carriesOver(s)` (used to build `carriedOutRows` from `rows`) requires `overtime_hours > 0`, which a rest day never has — so no total or carry-over row set is affected, only the displayed ledger, which no longer shows empty "OFF" rows for days that were simply not worked.

**`monthlyDetail()` dedupes shifts by `shift_date` before any other processing** (`dedupeByDate()`, keeping the shift with the latest `updated_at` per date): the app's whole data model assumes one shift per date (`isRestDay()`, `addShifts()`'s overwrite-by-date logic, etc.), but nothing enforces that server-side — there's no unique constraint on `(user_id, shift_date)` in `work_shifts`, so two devices/tabs creating a shift for the same date while both offline can each mint a genuinely separate row (different UUID) that later syncs successfully as two records. Found from a real duplicate in the user's own data (two identical shifts for the same date showing up twice in a PDF export). Left undeduped, a duplicate doesn't just render twice in "Détail des heures" — it silently doubles that day's contribution to *every* total downstream (`baseHours`, `night`, `overtime`, `offWorked`), since the original per-shift loop processed each array element independently with no notion of "one row per date". Deduping is deliberately a `pick` (keep the shift with the latest `updated_at`, discard the other), not a `sum`: summing the two would wrongly treat the duplicate as two real, distinct work periods, which the user confirmed it wasn't — just an unexplained bug, not intentional. `Number.isNaN(existingTime)` guards the comparison against a malformed/legacy `updated_at`: without it, `NaN >= x` is always `false`, so a corrupted-timestamp row picked first as "existing" could never be dislodged by a later, genuinely newer duplicate (caught in review). This fix only cleans up the view `monthlyDetail()` feeds (payroll simulator, PDF/Excel exports) — `Home.jsx`/`Calendar.jsx`/`summary.js`/`charts.js` read `shifts` directly from the store, not through `monthlyDetail()`, so a duplicate may still be visible/double-counted there until the extra row is deleted from the data itself (e.g. via `Calendar.jsx`'s day-detail panel). The root cause of *how* a duplicate gets created isn't fixed by this change — only its downstream effect on payroll math and the hours ledger.

**Payroll simulator** (`src/components/PayrollSimulator.jsx`, the "Paie" tab): the user enters an hourly rate (persisted in `localStorage` under `payroll:hourlyRate`, not synced — it's a simulation parameter, not domain data) and picks a month; `src/lib/payroll.js`'s `computePayroll(shifts, hourlyRate)` groups shifts by payroll month via `monthlyDetail()` (see the 25th-cutoff note above) and returns `[{key, label, rows, payroll}]`. `computeMonthPayroll()` splits pay into: base hours (rate ×1; worked-day-off hours are excluded from this — they're entirely inside the overtime pool, see below), a **monthly-tiered overtime pool** (`DEFAULT_RATES.overtimeThresholdHours = 33` — the first 33h at +25%, from the 34th hour on at +50%) that merges real overtime (`total.overtime`) **and** worked-day-off hours (`total.offWorked`) together (`overtimePoolHours = total.overtime + offWorkedHours`) before tiering, and a separate flat, untiered night bonus (+25% on `night_hours`, `hours × rate × 0.25`, not part of the pool or the 33h threshold). Worked-day-off hours were **not** always merged this way — an earlier version treated them as their own flat +25% bonus category excluded from the overtime pool entirely (mirroring the night-bonus mechanic), based on an earlier reading of a real payslip; corrected after the user clarified the employer counts worked-OFF-day hours as plain overtime, no distinction. `payrollRows(p)` is the single source of category rows shared by the UI, PDF, and Excel exports so none of the three recompute their own amounts; `offWorkedHours` is still exposed on the payroll result and shown via an informational "Dont heures travaillées en OFF (déjà incluses ci-dessous)" row (same `amount: null` pattern as the "Dont heures sup. du mois dernier" row below it) when `offWorkedHours > 0`, so the reader can see how much of the tiered total came from a worked OFF day without it being a separate paid category. The component prefetches `jspdf`/`xlsx` on mount (`useEffect(() => { import('jspdf'); import('xlsx') }, [])`) — on iOS Safari / an installed PWA, triggering a file download after an `await import(...)` network fetch can silently lose the "user activation" needed for the save to fire, so warming the module cache before the click matters; export errors render inline in the UI (not `alert()`, which is also silently swallowed in standalone PWA mode on iOS). The rate input keeps a separate `rateDraft` string (`type="text"`, `inputMode="decimal"`) rather than binding directly to the numeric `hourlyRate` state — a controlled `type="number"` input immediately strips a typed `,` on re-render, matching the same comma-input bug already solved elsewhere via draft state (`MissionForm.jsx`'s `tip_amount`, `MissionCard.jsx`'s `tipDraft`).

**"Mensualisé" pay mode** (`payroll:payMode` in `localStorage`, toggle at the top of the Paie tab): an alternative to the default "Heures réelles" base-hours calculation, added after comparing the simulator against a real bulletin de salaire from a salaried (mensualisé) employer. In this mode, `computeMonthPayroll()`'s base pay is no longer `total.baseHours × rate` but a fixed legal monthly base (`DEFAULT_RATES.weeklyBaseHours = 35` → `Math.round(35 × 52/12 * 100) / 100 = 151.67h`, editable per the same weekly figure in the UI, persisted under `payroll:weeklyBaseHours`), minus a manual per-month absence prorata (`payroll:absenceDays`, a `{monthKey: jours}` map — the app has no domain concept of a hire/end date, so this is a manual override) deducted at `(weeklyBaseHours / 7) × absenceDays`. That divisor is the legal daily rate (5h/day for 35h/week), **not** `monthlyBaseHours / 30` — verified to the cent against a real payslip where 14 calendar days of pre-hire absence (two full weeks) cost exactly 70.00h, not the 70.78h a `/30` proration would give. Overtime/night/off-worked bonuses are computed identically in both modes (they're supplements on top of base, not the base itself); `payrollRows()` swaps the "Heures normales" row for "Salaire de base (mensualisé)" (+ an "Absence prorata" row when `absenceDays > 0`) only in this mode. `PayrollSimulator.jsx`'s `updateAbsenceDays()` clamps to `Math.max(0, ...)` at the point of entry — a negative value would otherwise inflate `baseAmount` (subtracting a negative "absence") while `payrollRows()` only renders the offsetting "Absence prorata" row when `absenceDays > 0`, silently breaking the displayed total's arithmetic. `updateCotisationRate()` clamps the same way, for the same reason: a negative rate would make `cotisationAmount` negative, and both the UI and PDF prefix their own literal `−` before the displayed amount, so an unclamped negative value would render as a double sign (e.g. `−-118.00 €`) instead of a sensible number.

**Estimated net pay** (`DEFAULT_RATES.employeeCotisationRate` in `payroll.js`, editable as "Cotisations salariales (%, estimation)" in the Paie tab, persisted under `payroll:cotisationRate`): a single flat rate applied to `grossTotal` (`cotisationAmount = grossTotal × rate`, `netTotal = grossTotal - cotisationAmount`), deliberately **not** a line-by-line breakdown of the real deduction categories (santé/retraite/chômage/CSG-CRDS/mutuelle/exonérations heures sup...) — those are too specific to the employer's convention collective and change with the law to replicate reliably here. The default (23.1%) is derived from one real bulletin de salaire (non-cadre): brut 1179.05 € → net avant impôt 906.72 €. `computeMonthPayroll()` returns `cotisationRate`/`cotisationAmount`/`netTotal` alongside `grossTotal`, applied uniformly regardless of `payMode` (hourly or mensualisé) — these are **not** part of `payrollRows()` (which stays the set of categories that sum to `grossTotal`); instead the UI, PDF, and Excel each render "Cotisations salariales" and "Net estimé" as two extra lines after the "TOTAL BRUT ESTIMÉ" row, and the "Simulation indicative" disclaimer was reworded accordingly (still excludes `prélèvement à la source`, the individual income-tax withholding, which depends on a personal rate declared to the employer and isn't modeled at all).

**PDF export order** (`src/lib/exportPayroll.js`'s `exportPayrollPdf`): "Détail des heures" (day-by-day) renders *before* "Récapitulatif de paie" (category breakdown + TOTAL) — each gets its own amber-tab heading for visual symmetry now that neither is simply "whatever's under the page title". If the detail table fills close to a full page, a ~110mm minimum-height check (bumped from ~90mm when the cotisation/net-estimate rows were added below TOTAL BRUT ESTIMÉ) forces the recap onto a fresh page rather than letting it overlap the bottom margin. `exportPayrollXlsx` keeps the opposite order (rémunération detail first) — the two were deliberately *not* kept in sync here, per an explicit request to reorder only the PDF.

**Hours-only PDF export** (`exportPayrollPdf(payrollByMonth, hourlyRate, { hoursOnly: true })`): a second export button in `PayrollSimulator.jsx` ("PDF (heures)", next to Excel/PDF, styled with the same weight/contrast as the other two rather than a muted tertiary look) lets the user download just the day-by-day hours table (with its Total row) without the payroll amounts — useful for handing over a plain time sheet without the payroll simulation attached. `hoursOnly` swaps the title ("Détail des heures" vs "Simulation de paie"), skips the "Taux horaire" subtitle and the entire "Récapitulatif de paie" section, shows "Aucune heure enregistrée pour ce mois." if the month has no shifts, and saves as `detail-heures-*.pdf` instead of `simulation-paie-*.pdf`. The `hoursOnly` early-`return` sits inside `exportPayrollPdf`'s `payrollByMonth.forEach(...)` loop, so it only skips to the next month rather than exiting the whole function — this generalizes correctly even for a multi-month array (each month still gets its own title/details/total, no recap), since every iteration re-sets its own font/size/color state at the top and `doc.save()` runs once, after the loop. `exportPayrollXlsx` has no equivalent hours-only mode — the request was scoped to the PDF export only.

**Service worker registration** (`src/main.jsx`): registered explicitly via `virtual:pwa-register` (`registerSW({ immediate: true, onNeedRefresh() { updateSW(true) } })`) instead of relying on `vite-plugin-pwa`'s auto-injected default. With `registerType: 'autoUpdate'` (`vite.config.js`) and no custom handling, a new service worker silently takes over an already-open tab *without reloading it* — the page's JS module graph keeps pointing at the old content-hashed chunk filenames. Since `jspdf`/`xlsx` are dynamically imported (code-split, fetched on demand rather than on initial load), a tab left open across a deploy would 404 on export click with "Failed to fetch dynamically imported module" (worded differently per browser) — this is what surfaced as "L'export a échoué : Importing a module script failed." `updateSW(true)` forces an actual reload when an update is available, and `PayrollSimulator.jsx`'s `run()` additionally detects this specific error class (`isStaleChunkError()`) and calls `window.location.reload()` as a safety net for a tab that's *already* stale at the moment of failure (the `main.jsx` fix alone can't rescue a tab that's already broken when the user clicks export).

**Export** (`src/lib/exportPayroll.js`): the hours-only export that used to live in `Home.jsx` (`exportData.js`'s `ExportSection`) has been retired — `exportPayrollPdf`/`exportPayrollXlsx` now generate the payroll summary *and* the day-by-day hours detail (shared row-formatting helpers in `src/lib/shiftRows.js`, `SHIFT_TABLE_HEAD`/`shiftRowCells`, plus `shiftTotalsRow()` for the trailing "Total" row summing `Durée`/`Sup`/`OFF trav.`/`Nuit` across the month's shifts — rendered with an amber-tinted bold row in the PDF, a plain trailing row in Excel) in one `.pdf` (via `jspdf`) or `.xlsx` (via `xlsx`) file, both dynamically imported to keep them out of the main bundle. `SHIFT_TABLE_HEAD` has no "Sup nuit" column (heures sup that are also night hours) — it existed briefly but was removed on request: it was never factored into any payroll calculation (`computeMonthPayroll()` only ever reads `total.night`, never a night-overtime figure) and, sitting next to both "Sup" and "Nuit", read as a confusing third overlapping category rather than useful information. `monthlyDetail()`'s `total.nightOvertime` was removed alongside it (had no other consumer — `shiftTotalsRow()`'s own "Nuit"/"Sup nuit" sums were always derived independently from raw shift rows, never from `total.nightOvertime`, so it was already dead weight even before this cleanup). The PDF's column x-positions (`detailX` in `exportPayrollPdf`) were respread across the table's full width rather than just dropping the last column's position, to avoid leaving an empty gap on the right. Both take the `[{key, label, rows, payroll}]` shape produced by `computePayroll()`. The PDF's "Récapitulatif de paie" table draws its horizontal gridlines from the actual accumulated row-bottom y-positions (`rowBottoms` array in `exportPayrollPdf`) rather than a fixed row-height step — needed once that table gained non-uniform row heights (`TOTAL BRUT ESTIMÉ`/`NET ESTIMÉ` are taller than the category/cotisation rows), which a fixed-step loop can't track without drifting or dropping a boundary (found and fixed across three review passes: a misaligned grid, then a missing internal boundary).

**`payrollRows()` labels must stay ASCII-only** (`src/lib/payroll.js`): jsPDF's base-14 fonts (Helvetica) only support WinAnsi/CP1252 encoding — a `≤` character in a category label rendered as garbled text in the exported PDF. Labels are spelled out in French ("jusqu'à 33h" / "à partir de 34h") instead of using math symbols; since `payrollRows()` is the shared source for the UI, PDF, and Excel, this also keeps the on-screen simulator readable rather than terse.

**The installed `xlsx` (community edition, `^0.18.5`) silently drops all cell styling on write** — verified empirically by writing a `.s` (font/fill/border) style and inspecting the raw `styles.xml`: the style is dropped and every cell falls back to the default. Do not add `.s` assignments to `exportPayrollXlsx`, they're dead code. Number-format codes (`.z`, e.g. `'#,##0.00" €"'`) *do* work and round-trip correctly — that's the only real formatting lever available, so the Excel export gets its visual hierarchy from structure alone (ALL-CAPS section titles isolated by blank rows, correct column widths sized to the longest label, real sheet-tab names via `monthlyDetail()`'s `sheet` field). The PDF, by contrast, gets full amber-branded styling (`AMBER`/`AMBER_TINT`/`ZEBRA_TINT` constants in `exportPayroll.js`, zebra-striped and bordered detail table) since jsPDF has no such limitation.

**Dispatch split** (`src/lib/dispatch.js`): `DISPATCH_RATE` (10%) is applied to compute the share owed back to dispatch vs. net kept. `lastMonthTips()` scopes this to the previous calendar month only (used by `Home.jsx`'s "Partage dispatch" section). An older all-history variant, `tipsByMonth()`, was removed as unused dead code in the same cleanup pass as `aggregate.js`.

**`SyncBar` (top status bar in `App.jsx`) pads for the safe-area-top inset, not just the bottom `TabBar`.** `index.html`'s `apple-mobile-web-app-status-bar-style: black-translucent` (+ `viewport-fit=cover`) makes iOS draw page content underneath the status bar/Dynamic Island, so any `sticky top-0` element needs its own `env(safe-area-inset-top)` padding or it renders partially hidden behind it — found when the "Déconnexion" button added to `SyncBar` was unreachable on a Dynamic Island phone. `pt-[max(0.5rem,env(safe-area-inset-top))]` on `SyncBar` fixes it, mirroring `TabBar`'s pre-existing `pb-[max(0.25rem,env(safe-area-inset-bottom))]` for the bottom safe area.

**A `beforeunload` guard in `App.jsx`** warns before leaving/refreshing the page while `pending > 0` (from `useSyncStatus`, i.e. any mission/shift still `pending`/`error`/`pending-delete`) — added after a report of data entered in Safari **Private Browsing** disappearing on refresh. Private Browsing is known to be unreliable for this app's storage model: both the Supabase auth session (`localStorage`) and the Dexie/IndexedDB cache can fail to persist a very recent write across a reload in that mode (older, already-settled data survives; the just-written row doesn't), which also explains why the user was asked to log in again right when the new shift vanished. This isn't fixable from app code — the underlying storage APIs report success but Safari's private-mode backend doesn't actually keep the data — so the guard is a mitigation (catches "refreshed right after saving, before it reached the server") rather than a fix; using a normal Safari tab or the installed Home Screen PWA avoids the underlying issue entirely.

**Only `App.jsx`'s import graph is live.** It renders `Auth`, `Home`, `Calendar`, `MissionsList`, `PayrollSimulator` (the four `TabBar` tabs: Accueil/Calendrier/Missions/Paie), plus `MissionForm`/`ImportModal` as modals — that's the entire component tree. If you're exploring `src/components/`, don't assume a file is wired in just because it exists; verify it's reachable from `App.jsx` before treating its logic as current behavior. (Five stale/superseded components — `Charts.jsx`, `Stats.jsx`, `DayTotal.jsx`, `Shifts.jsx`, `ImportReport.jsx` — were removed for this reason; their functionality is already covered by `Home.jsx`, `Calendar.jsx`, and `ImportModal.jsx`.) `App.jsx` also renders `<Analytics />` from `@vercel/analytics/react` (page-view analytics, unrelated to the offline-sync layer).

## Review subagents

Since there's no test suite, review is the only correctness gate before shipping. Two project subagents (`.claude/agents/`) exist for this — use `sync-invariant-reviewer` proactively after any change to `src/lib/sync.js`, `src/lib/db.js`, `src/store/missions.js`, or any `save*`/`delete*` function for missions/shifts (it checks the pending/error/pending-delete state machine and the "don't clobber locally-dirty rows on pull" rule); use `code-reviewer` for everything else.
